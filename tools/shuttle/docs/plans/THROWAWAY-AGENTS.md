# Throwaway agents (design, 2026-11-07)

Status: implemented in fork commit 59 (branch `sh/throwaway-agents`, 2026-11-07). One finding while building: Chromium writes an in-memory partition's GPU shader caches to disk; they are deleted with the agent and at startup. Requested by the maintainer on 2026-11-06.

## Goal

A short-lived agent for a one-off job: an agent creates it, uses it and forgets it, and the browser cleans up.

```
create-agent { throwaway: true, idleMinutes?: 15, name?: "Scraper", color?: "cyan" }
  -> { id: "tmp-3f9a1c0b7d2e", throwaway: true, idleMinutes: 15, expiresAt: "...", ... }
```

- Deleted automatically after `idleMinutes` (default 15) without activity.
- Listed on chrome://agents like any agent, marked as temporary.
- No avatar fetch.
- At most 50 live throwaway agents (configurable).

## Behaviour

| Topic | Throwaway agent |
| --- | --- |
| Id | Always generated by the browser: `tmp-<12 hex>` (random). `id` is refused with `throwaway: true`. Persistent agents can't use the `tmp-` prefix. So an id is never reused (see Storage). |
| Storage | **In-memory** StoragePartition (`StoragePartitionConfig::Create(profile, "shuttle-<id>", "", /*in_memory=*/true)`). Cookies, local storage and cache never reach the disk. A crash or restart leaves nothing behind. |
| Registry | Kept in memory in `ProfileRegistry` (a map next to the `shuttle.profiles` pref), never written to prefs. Gone after a restart, together with its storage. |
| Identity | `name` and `color` as usual (name defaults to the id). `avatar` is refused, so nothing is fetched and the tab group shows only name and color. `persistSessionCookies` is refused (there is no disk). |
| Lifetime | Deleted `idleMinutes` (1-1440, default 15) after its last activity. Activity uses the same signals as sessions: MCP calls naming its sessions or tabs, CDP client messages, a running tool call, a person looking at one of its tabs. With no open session, the clock runs from the moment the last session closed (or from creation). Deleting closes its sessions and tabs (discard, no beforeunload). `delete-agent` works at any time. |
| Sessions | `open-session` as usual. A session's own idle timeout still applies. The agent outlives its sessions until its own idle time is up, so an agent can close a session and open a new one on the same storage. |
| `list-agents` (MCP) | Listed, with `throwaway: true`, `idleMinutes` and `expiresAt` (an estimate: last activity + `idleMinutes`). |
| chrome://agents | Listed as usual, with a "Temporary" indicator (an icon with a tooltip that gives the expiry) on the agent card. Its sessions are listed as usual. |
| Tab context menu "Hand to agent" | Offered like any agent (the tab reopens in the throwaway's in-memory storage). |
| Cap | At most 50 live throwaway agents; `create-agent` refuses beyond that ("delete one or wait for one to expire"). `--shuttle-max-throwaway-agents=<n>` changes it (0 = throwaways off). |
| Tab strip | Its tabs form a tab group with its name and color, like any agent's, so a person can still see who is working. |
| `update-agent` | `name`, `color` and `idleMinutes` only. Converting between throwaway and persistent is not supported: an in-memory partition can't become a disk one. |
| `state-save` / `state-load` | Refused for throwaway agents: a saved state is cookies on disk, which defeats the point. |
| `save-text { to: "file" }` | Allowed. `shuttle/secrets/<id>/` is deleted together with the agent (on expiry and on `delete-agent`), and at the next start for throwaways that didn't get to it (crash): any `secrets/tmp-*` directory without a live agent goes. The tool description says so. |

## Implementation

Conventionally about 3 to 4 engineer days; at our pace about 3 to 4 session hours. On top of that come one Mac dev build, an SH-Review round and the maintainer's answers to the questions below.

1. **`ProfileRegistry`** (`profile_registry.{h,cc}`):
   - `Entry::throwaway` and `std::map<std::string, Entry> throwaway_`.
   - `Exists` / `Get` / `List` cover both stores. `CreateThrowaway(const Identity&)` returns the generated id.
   - `PartitionConfig(id)` returns `in_memory = true` for throwaways.
   - `Delete` for a throwaway: drop the entry, then clear its partition with `StoragePartition::ClearData` (all types). This frees memory and defends in depth against id reuse. No obliterate and no pending-delete pref.
   - `IsValidId` stays as it is. `create-agent` without `throwaway` refuses `tmp-`.
2. **In-memory partition checks**: `IdForConfig` (`profile_registry.cc`) and `IsAgentWebContents` (`agent_partition.cc`) currently reject `in_memory` configs. Accept them when the id is a registered throwaway. `ShouldPersistSessionCookies` is not involved (no cookie file).
   - Users of `IsAgentWebContents`: `chrome_content_browser_client.cc:6384` and `browser_navigator.cc:637`, so throwaway tabs get the same agent treatment (no external apps, popups stay in the session).
3. **Expiry** (`session_manager.{h,cc}`):
   - Track per-agent `last_activity_ticks`: updated by `Touch`/`EndWork` of any of its sessions, and when its last session closes.
   - `CheckIdle` (already on a timer while sessions have a timeout) also runs while a throwaway exists. It deletes throwaways with no running call, no tab in front of the user and 15 min idle, through the same path as `delete-agent` (`CloseProfileSessions` + `Delete`).
   - `idleMinutes` per agent; `--shuttle-throwaway-idle-timeout=<n>s` overrides it for probes (like `--shuttle-session-idle-timeout`).
   - Deletion also removes `shuttle/secrets/<id>/` on the blocking pool, through the profile-dir anchor (`O_NOFOLLOW`, never through a link; `base::DeletePathRecursively` on the opened chain is not enough: walk with `unlinkat`/`openat`). At startup, `secrets/tmp-*` without a live agent are removed the same way.
4. **MCP** (`mcp_tools.cc`):
   - `create-agent`: `throwaway` (boolean), `idleMinutes` (integer 1-1440, throwaway only). With `throwaway`, `id`, `avatar` and `persistSessionCookies` are refused. Refused beyond the cap.
   - `DescribeAgent` adds `throwaway`, `idleMinutes` and `expiresAt`.
   - `update-agent` refuses `avatar` / `persistSessionCookies` for throwaways.
   - The `state-save` / `state-load` path in `page_tools.cc` refuses throwaways.
   - Tool descriptions and `docs/MCP.md` updated.
5. **UI**: chrome://agents (`chrome/browser/resources/agents/app.html.ts`, `app.css`): a "Temporary" icon on throwaway cards with a tooltip ("Deleted after N min without activity, about HH:MM"); no edit for avatar/cookie settings on them. `AvatarCache` never sees an avatar (refused at creation). The cap is `--shuttle-max-throwaway-agents` (`switches.h`, default 50).
6. **Probe**: `smoke-throwaway.mjs` (own launch in `smoke-all`, `--shuttle-throwaway-idle-timeout=8s`) checks:
   - create without id: `tmp-` id, `throwaway: true`, `idleMinutes` 15;
   - `id` / `avatar` / `persistSessionCookies` refused, `idleMinutes` out of range refused;
   - the cap (launch with `--shuttle-max-throwaway-agents=2`: the third create is refused);
   - its save-text file is gone after `delete-agent`;
   - listed on chrome://agents with the temporary indicator;
   - a cookie set in its tab is not in the profile's `Cookies` DB on disk;
   - an idle session keeps it until the timeout, then the agent and its tabs are gone;
   - activity resets the clock;
   - `delete-agent` works;
   - `state-save` refused.

   Plus a restart check in phase 2 of the MCP smoke: no throwaway survives.
7. Docs: `MCP.md`, `FEATURES.md` row, `REMOVAL-LOG` fork commit entry.

## Risks

- **Memory after deletion.** Chromium never unloads a StoragePartition. A deleted throwaway's (cleared) partition and its network context stay in memory until the browser restarts. This is the same as for deleted persistent agents today (`gc_required_`). Cost per partition: an empty network context, roughly 1 to 2 MB (to measure in the probe). The cap bounds live throwaways, not deleted ones: hundreds a day on a long-running browser still add up. If the measurement says so, a follow-up could recycle a cleared partition for the next throwaway (pool) instead of creating a new one.
- **In-memory partitions are a less tested Chromium path for full browser tabs** (guest views and incognito-like uses rely on them). Watch for service workers, IndexedDB and cache quirks in the first smoke.
- **Id reuse with an in-memory partition** would hand old cookies to a new agent (same config, same partition). Random ids, the reserved `tmp-` prefix and `ClearData` on delete rule this out.

## Decisions (maintainer, 2026-11-07)

1. `idleMinutes` optional, default 15.
2. A throwaway's `save-text` files are deleted with it.
3. Shown on chrome://agents as usual, with a temporary indicator.
4. Cap of 50 live throwaways, configurable.
